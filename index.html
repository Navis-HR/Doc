Overview

NAVISHR Backend is a NestJS API for a multi-tenant HR platform. It provides authentication, tenant management, role and permission based access control, employee profile management, organization departments, task/project management, notifications, news publishing, file storage, and a performance management suite.

The application uses PostgreSQL through TypeORM, JWT bearer authentication through Passport, Swagger, global DTO validation, response serialization, and S3-compatible object storage for uploaded files.

Core Workflows

Tenant and Authentication

  1. A tenant is created through /tenants.
  2. Users register through /auth/register; the tenant is taken from x-tenant-id or from the DTO.
  3. Users log in through /auth/login.
  4. The API returns a JWT containing the user identity and tenant context.
  5. Protected endpoints validate the JWT, load the user role and permissions, and authorize through PermissionsGuard or RolesGuard where decorators are present.

Role and Permission Management

  1. Permissions are seeded from src/database/seeds/permission.seed.data.ts.
  2. Roles are created with attached permissions.
  3. Auth users are assigned a role.
  4. Decorated endpoints require permission names such as task:create, user:view, or performance:cycle:activate.

Employee Profile and Organization

  1. auth_users stores login and account status.
  2. user_info stores employee profile data and links one-to-one with auth_users.
  3. departments group users by tenant.
  4. reportingToId supports employee hierarchy and manager reporting chains.

Task Management

  1. A tenant creates projects, epics, sprints, and task statuses.
  2. Tasks are created under a project and status, with optional epic, sprint, parent task, due date, and priority.
  3. Tasks can be assigned to employees, including cross-department assignments.
  4. Comments, mentions, attachments, watchers, and activity logs provide collaboration and audit history.
  5. Notifications can be created for task-related events.

Performance Management

  1. Admins define performance templates for departments.
  2. Templates contain KRAs, focus areas, KPIs, checklists, and checklist rules.
  3. Cycles and periods define the performance calendar.
  4. Employee plans are created from templates for a cycle.
  5. Targets are assigned for plan checklist items and periods.
  6. Employees submit achievements against targets.
  7. Reviewers approve or reject achievements.
  8. Evaluations calculate performance scores, and dashboard endpoints expose summaries.

News Publishing

  1. Categories are created through news-category.
  2. News posts are authored, updated, and deleted through news-post.
  3. Public listing and slug based retrieval are available for published content flows.

File Storage

  1. Files are uploaded to S3-compatible storage through /storage/public or /storage/private.
  2. Uploaded files are validated by storage utilities.
  3. Public uploads return direct URLs; private files can be accessed through signed URLs.
  4. Task and task comment attachment endpoints store file metadata linked to task records.

Notes and Recommendations

  • synchronize: true should be replaced with migrations before production use.
  • JWT_SECRET falls back to superSecretKey in code. Production deployments should require a strong secret and fail fast if missing.
  • JWT_EXPIRES_IN exists in .env, but the JWT module currently uses a hard-coded 1d expiration.
  • Two TaskAttachment entity files map to task_attachments; this can cause maintenance drift and should be consolidated.
  • SMTP variables exist in .env, but no SMTP service usage was found in the current source.
